# 15 — claude-code-unified-agents

## En-tête
- **Nom** : claude-code-unified-agents
- **Chemin** : `references/claude-code-unified-agents/` (les agents vivent dans le sous-dossier imbriqué `…/claude-code-unified-agents/.claude/agents/`)
- **Type** : Collection d'agents Claude Code spécialisés, configurés comme agents de production, pilotés par un agent orchestrateur racine.
- **Langage principal** : Markdown (frontmatter YAML `name/description/category/tools` + prompts) ; certains agents embarquent du code d'exemple TypeScript/YAML.
- **Statistiques** : **53 fichiers agents `.md`** vérifiés par `find` (et non 54 comme l'annonçait l'ancienne fiche), répartis sur 7 catégories + 1 orchestrateur racine ; 57 fichiers `.md` au total dans le dépôt. **4 agents promis par le README n'existent pas** : `ui-designer`, `content-strategist`, `performance-optimizer`, `iot-engineer`.

## Synthèse
La fiche précédente promettait « 54 prompts spécialisés hautement réutilisables » mais n'en citait **aucun**, ne pointait vers aucun fichier, et se contentait de paraphraser le README (« backend/frontend/DevOps »). L'audit approfondi révèle deux choses que l'ancienne fiche taisait :

1. **Le compte exact est 53 agents, pas 54**, et 4 agents promis (`ui-designer`, `content-strategist`, `performance-optimizer`, `iot-engineer`) sont absents du dépôt.
2. **Les fichiers se divisent en deux familles radicalement différentes**, ce qui change radicalement l'évaluation de réutilisabilité :
   - **Famille « prompt pur » (49–185 lignes)** — frontmatter YAML + sections standardisées (`## Core Expertise` / `## Approach` / `## Best Practices` / `## Output Format`). Ce sont de **vrais system_prompts directement adaptables** : `python-pro`, `code-reviewer`, `security-auditor`, `test-engineer`, `frontend-specialist`, `backend-architect`, `orchestrator`, `devops-engineer`. Haute valeur.
   - **Famille « code trophy » (1000–1650 lignes)** — un en-tête prompt de ~30 lignes puis 95 % de code TypeScript/YAML (`ContextManager` class, framework Playwright complet, configs CI…). La valeur prompt est faible ; c'est du scaffolding non portable : `e2e-test-specialist`, `context-manager`, `error-detective`, `workflow-optimizer`, `agent-generator`, `api-designer`.

La valeur réelle est donc **concentrée dans ~8 prompts « purs »** alignés avec les rôles de `graph-orchestrator-smolagents` (Router/Architect/Coder/Tester/Judge/Security). **Note de réutilisabilité globale : Moyenne** (et non Haute comme l'ancienne fiche) : les bons prompts sont 🟢, mais ils restent **souples** (peu de « hard gates » bloquants), ils ne sont pas pensés pour une stack DSPy+smolagents (pas de notion de signature ni d'outils typés), et la majorité des 53 fichiers est du code TS non portable. Le portage demande une **réécriture structurelle**, pas un copier-coller.

## Exclusions conscientes
- **Fichiers « code trophy »** (`e2e-test-specialist` 997 lignes, `context-manager` 970 lignes, `workflow-optimizer`, `error-detective` hors en-tête, `agent-generator` hors en-tête, `performance-tester`, `accessibility-auditor`, `api-designer`) : 90-95 % de code TypeScript/YAML non portable en Python smolagents — seule la première trentaine de lignes (prompt) est conservée en section doc.
- **Catégories hors périmètre code-generation** : la majorité de `infrastructure/` (cloud-architect, kubernetes-expert, monitoring-specialist, deployment-manager, performance-engineer), `business/` (project-manager, product-strategist, business-analyst, requirements-analyst, technical-writer) et `data-ai/` (ai-engineer, data-engineer) — aucun rôle correspondant dans le graphe cible.
- **Agents promis mais absents** : `ui-designer`, `content-strategist`, `performance-optimizer`, `iot-engineer` (le README compte 54 agents ; le dépôt en contient 53).
- `node_modules/`, `package*.json`, configs Webpack/Vite : écosystème Node, non pertinent.

## Correspondance avec `plan_usine_logicielle.md`
- **Priorité 0 (Spécialisation des agents)** : les 7 prompts 🟢 (`orchestrator`, `backend-architect`, `python-pro`, `frontend-specialist`, `test-engineer`, `code-reviewer`, `security-auditor`) sont les squelettes directs pour spécialiser la flotte actuelle ; le `AgentCapabilitySchema` de `agent-generator` fournit le modèle de déclaration.
- **Priorité 6 (Judge / Code Review anti-bruit)** : `code-reviewer.md` (output structuré Critical/Major/Minor, profil lecture seule) est l'inspiration directe du format de sortie du Judge.
- **Recommandation** : repartir des 7 prompts 🟢 comme squelettes, leur injecter des garde-fous **plus durs** (le projet cible parle de gates Judge/Security — il faut des règles bloquantes, pas des « best practices »), et s'inspirer du `AgentCapabilitySchema` pour formaliser la déclaration des rôles dans le graphe.
